这一章把一个真实转储的完整处理过程走一遍，**包括我走错的每一步**。

案例：某角色的模型，包含身体、两段布料、一把长枪。

::: tip 第一个关键发现：主目录全是快捷方式
根目录 8076 个文件名形如 `000038-ib=7ad7e69e-vs=...-ps=...buf.lnk`，都是 **Windows 快捷方式**（1~1.5 KB），指向 `deduped\` 里的真实文件。

而 `deduped\` 里的文件名是**内容 hash**（如 `9c2ac78e.buf`），不是资源 hash。

**逻辑名 → 真实文件** 的映射只能从 `log.txt` 的 `Dumping Buffer` 行取。
:::

### topology 分布

这是判断「这个游戏有没有 GPU 预蒙皮」最快的方法：

```powershell
Get-ChildItem deduped\*.txt |
  Select-String -Pattern 'topology: (\w+)' |
  ForEach-Object { $_.Matches[0].Groups[1].Value } |
  Group-Object | Select-Object Name, Count
```

结果：**trianglelist 235 个 / pointlist 8 个**。

::: danger 有 pointlist 就说明有 GPU 预蒙皮
8 个 pointlist 的 txt 全都来自 `layout=d8e9f34b`：

```
1569d000-vb0-layout=d8e9f34b-topology=pointlist-stride=40-count=24068.txt
47280c51-vb1-layout=d8e9f34b-topology=pointlist-stride=32-count=24068.txt
```

24068 正好和后面 trianglelist 的顶点数一致 → 这就是同一个模型的 **T-pose 缓冲**。
:::

### 锁定目标 IB

`7ad7e69e.buf` = 177636 字节 = **88818 个 R16_UINT 索引**。

配套 4 个 txt：

| 文件 | first | count |
|---|---|---|
| `7ad7e69e-ib-format=R16_UINT-topology=trianglelist-count=59307.txt` | 0（无后缀） | 59307 |
| `...-first=59307-count=10446.txt` | 59307 | 10446 |
| `...-first=69753-count=18045.txt` | 69753 | 18045 |
| `...-first=87798-count=1020.txt` | 87798 | 1020 |

合计 59307 + 10446 + 18045 + 1020 = **88818** ✓

## 第 2 步：列出所有引用该 IB 的 draw

**16 个 draw** 引用了这个 IB：

```
000038 000039 000041 000048 000049 000050 000052 000059
000098 000100 000103 000104 000109 000111 000114 000115
```

从 `log.txt` 的 `DrawIndexed` 行取参数：

```
000038 DrawIndexed(IndexCount:10446, StartIndexLocation:59307, BaseVertexLocation:0)
```

16 个 draw 分成 4 套 layout × 4 段 IB：

| layout | draws |
|---|---|
| `5bfd1268` | 000038 000039 000041 000048 |
| `bac6075e` | 000049 000050 000052 000059 |
| `7e80b6e1` | 000098 000100 000103 000104（三槽） |
| `8456ccca` | 000109 000111 000114 000115（三槽） |

::: tip 为什么是 4×4 的正交组合
4 个 draw pass（主渲染 / 阴影 / 描边 / 深度）各自需要 4 段 IB。

同一段 IB 在 4 个 pass 里各被一个 draw 使用。
:::

## 第 3 步：对比 4 套 layout

这是决定「用哪套布局」的关键一步。

| layout | vb0 分组后 | vb1 分组后 | 结论 |
|---|---|---|---|
| `5bfd1268` | POSITION@0 + NORMAL@12 = **stride 24** | COLOR@0 + TEXCOORD@4 + TEXCOORD1@12 + TEXCOORD2@20 = **28** | vb0 声明 40 但只用到 24 ✗ |
| `bac6075e` | POSITION@0 + NORMAL@12 + TANGENT@24 = **40** ✓ | 同 5bfd1268 = **28** ✓ | ✓ 两槽都刚好凑满 |
| `7e80b6e1` | POSITION@0 = 12 | COLOR + TEXCOORD×3 = 28 | 三槽拆分 |
| `8456ccca` | POSITION@0 + TANGENT@24 = 40 | COLOR@0 + TEXCOORD@4 = 12 | 三槽拆分 |

::: danger 为什么 5bfd1268 不行
它的 vb0 txt 里声明 `stride=40`，但按 InputSlot 分组后 slot0 只有 `POSITION@0` 和 `NORMAL@12` —— 到 24 就结束了。

剩下的 16 字节没被任何 element 覆盖。

那 16 字节里确有数据（就是 TANGENT），只是这份 InputLayout **没把 TANGENT 声明进 slot0**，而是声明在 `@0`（和 POSITION 撞车）—— 那是 shader 用其它方式算的切线，不是从 buffer 读的。

**选它的后果**：vb0 的 stride 40 里后 16 字节读不到语义 → 模型缺失切线 → 光照错乱。
:::

**选 `bac6075e`** —— 它是唯一一套 vb0 单独就能凑满 40 字节的（12 + 12 + 16 = 40）。

## 第 4 步：验证真实 stride（反查法）

txt 里写的不一定可信。用 `vertex-data` 预览的**真实数值**反查 buffer：

```
vb0[0] POSITION=(-0.529100716, -0.042438779, 0.0551764071)
vb0[0] NORMAL=(-0.572330952, -0.784330904, 0.239292696)
vb0[1] POSITION=(-0.530644715, -0.0411315858, 0.0557684004)
```

在 `1569d000.buf` 里搜这四个断言：

```python
import numpy as np

raw = open('deduped/1569d000.buf', 'rb').read()
f = np.frombuffer(raw, dtype='<f4')

targets = [
    (-0.529100716, 0),      # 顶点0 POSITION 起点
    (-0.572330952, 3),      # 顶点0 NORMAL 起点（offset/4 = 3）
    (-0.530644715, 10),     # 顶点1 POSITION 起点
]

for stride_f in range(4, 40):
    ok = all(abs(f[t[1] + (0 if t[1] < 3 else stride_f // 4)] -
                 t[0]) < 1e-5 for t in targets)
    print(f'stride={stride_f*4}: {"✓" if ok else ""}')
```

结果：

| stride | 命中 |
|---|---|
| **40** | ✓ 4 个断言全命中 |
| 80 | 只命中 1 个（NORMAL 偶然对齐） |

→ **stride = 40**，且 `POSITION@0`、`NORMAL@12`、`TANGENT@24`。

顶点数：`962720 / 40 = 24068` ✓

vb1 同样方法：`673904 / 28 = 24068` ✓（`TEXCOORD@4` 的 `(0.00442296267, 0.753909111)` 命中）

::: tip 两个 count 不一样是正常的
txt 里写的 `count=18531` / `23866` / `16255` 是**该 draw 视角下引用的顶点数**，不是缓冲全量。

`24068` 才是这个池子的真实大小。

deduped 里有 4 个不同 count 的 vb0 txt，都是同一个 buffer 被不同 draw 以不同子集引用。
:::

## 第 5 步（重大转折）：发现双份顶点缓冲

我一开始照 `bac6075e` 的三角形布局提取，渲染出来是**一个踢腿姿势的角色**。

顶点数对、布局对、索引也对，可姿势就是动作中的某一帧。问题不在提取，在于**拿错了那一份顶点**。

### 找到 T-pose 缓冲

回头看那 8 个 pointlist txt：`layout=d8e9f34b`，两个缓冲：

| 文件 | stride | 内容 |
|---|---|---|
| `1569d000.buf` | 40 | POSITION@0(12) + NORMAL@12(12) + TANGENT@24(16) |
| `47280c51.buf` | 32 | BLENDWEIGHT@0(16) R32G32B32A32_FLOAT + BLENDINDICES@16(16) R32G32B32A32_SINT |

对比已蒙皮的版本（`bac6075e`）：

| | T-pose（pointlist） | 已蒙皮（trianglelist） |
|---|---|---|
| vb0 | `1569d000.buf` stride 40 | `9c2ac78e.buf` stride 40 |
| vb1 | `47280c51.buf` stride 32（权重） | `9798ab34.buf` stride 28（UV + COLOR） |

### 决定性证据

用**同一个 IB 的索引**分别索引两份 vb0，渲染出来：

- T-pose 缓冲 → 站姿 T-pose，尺寸 `[0.832, 1.617, 1.117]`
- 已蒙皮缓冲 → 踢腿姿势，尺寸 `[1.602, 0.713, 0.565]`

**两张图都是完整人形** → 顶点顺序完全一致，只是坐标不同。

::: danger 这一步推翻了两个错误结论
**错误一：up 轴是 X**

我之前用「沿轴切片的横截面宽厚比」判出 up = X（比值 1.11，其它两轴 2.35 / 2.08）。

那是因为**用了已蒙皮的缓冲** —— 腿伸向 X 方向，把 X 拉成了最长轴，切片自然看起来「横截面圆」。

T-pose 下 **Y 才是身高方向**（尺寸 1.617 在 Y 轴），用标准变换 `(x,y,z) → (x,-z,y)` 即可。

**错误二：数据类型是 CPU-PreSkinning**

从 trianglelist 视角看不到 BLEND 语义，我判定这是 CPU 预蒙皮。错。

**看不到骨骼绑定数据 ≠ 没有骨骼绑定** —— 那份是游戏在 GPU 上蒙完皮之后的结果，权重早就用掉了。

真正的数据类型是 **GPU-PreSkinning**：
`GPU_P12_N12_TA16_C4_T8_T1-8_T2-8_BW16_BI16_`
:::

### 这也解释了 SSMT4 为什么要混标

| Category | 从哪份缓冲取 | ExtractTechnique |
|---|---|---|
| Position | T-pose vb0（stride 40） | `pointlist` |
| Blend | T-pose vb1（stride 32） | `pointlist` |
| Texcoord | 已蒙皮 vb1（stride 28） | `trianglelist` |

**要 T-pose 的形状 + 骨骼权重，同时还要原始 UV。**

UV 只在已蒙皮的 vb1 里（T-pose 的 vb1 是纯权重缓冲，28 vs 32 字节）。

## 第 6 步：找到 T-pose 缓冲对应的 draw

原理：**vb0 的 hash 反查日志**。

```python

first_tl = '000038'

# 2. 在该 draw 的日志行里找 IASetVertexBuffers
#    "0: resource=... hash=9c2ac78e"    ← 已蒙皮的 vb0
# 3. 扫全部日志行，找 hash=9c2ac78e 的行（排除 Dst）
# 4. 其中 draw index < first_tl 的，取最后一个
```

结果：pointlist draw 是 **000001 ~ 000005**（`vs=653c63ba4a73ca8b`）。

::: danger 必须排除 CopyResource 的 Dst 行
日志里有这种行：

```
000007 CopyResource(pDstResource:0x..., pSrcResource:0x...)
Src: resource=... hash=e4d2fec9
Dst: resource=... hash=e9d29b50
```

`Dst` 是「拷贝目标」，不是「预蒙皮的输入」。把 Dst 也算进去会匹配到错误的 draw。
:::

### 踩过的三个坑

::: danger 坑 1：Blender 4.5 运行脚本直接闪退
手工拼拓扑：

```python

me.polygons.add(m)

```

4.x 里 `loop_total` 是只读派生属性，写不进去，于是 loop 和多边形的对应关系无效 → `update(calc_edges=True)` 遍历边表越界 → 进程被系统杀掉。

**改用 `me.from_pydata()`。**
:::

::: danger 坑 2：没有顶点组
`spec['global_indices']` 从 JSON 读出来是 Python `list`，而代码写的是 `weights[gidx[vidx]]` —— numpy 数组用 list 索引会抛：

```

```

异常被外层 `try/except` 吞掉，只记一行日志就跳过后续所有步骤（顶点组、材质、自定义属性全没了）。

**先 `np.asarray(gidx, dtype=np.int64)`。**
:::

::: danger 坑 3：顶点色变成彩虹碎片
见[顶点色与 UV](/guide/blender/vertex-color)。

根因：`BYTE_COLOR` 底层 4×u8，传 float32 会把字节劈裂。

我修了两次 —— 第一次的回读校验因为 `foreach_get` / `foreach_set` 对称而永远通过，没用。
:::

## 这个案例的教训

### 1. 先看 topology 分布

有 pointlist → GPU 预蒙皮 → 坐标和权重去 pointlist 的缓冲拿。

这一步做错，后面全错（我在这上面浪费了一整轮，模型带踢腿姿势）。

### 2. 布局要按 InputSlot 分组后看

同一个 vbN txt 里抄着**完整的 InputLayout**（所有 slot 的元素都在），还有重复 offset 和撞车 offset。

直接按行读会得到错误的 stride。

### 3. up 轴不要用「最长轴」判

用「沿该轴切片的横截面宽厚比 ≈ 1」，而且**必须用 T-pose 的缓冲**。

### 4. striding 和 count 都别信 txt

stride 用 `vertex-data` 反查，count 用 `len(buf) // stride`。

### 5. 顶点色的坑有两层

第一层是类型不匹配（劈裂），第二层是**校验会骗你**。

### 6. 回读校验的基准要用原始字节

任何「我写进去又读出来一样」的校验，如果写读是对称的，永远通过。
