# 抓取一次转储

这一节讲怎么让 3DMigoto 在**你想要的时刻**、把**你想要的东西**dump 下来。

## `d3dx.ini` 里跟提取相关的配置

3DMigoto 的配置文件叫 `d3dx.ini`，跟 `d3d11.dll` 放在一起。跟 FrameAnalysis 有关的段落大致是：

```ini
[Logging]
calls=1
dump_calls=0
dump_include_vertex_buffers=1

[Hunting]
hunting=1
```

逐个说：

### `calls=1`

打开调用日志。**必须开** —— 没有 log，你就无法建立「资源哈希 → 文件」的映射。

### `dump_include_vertex_buffers=1`

把顶点缓冲也一起 dump。不开的话只有索引和纹理，模型就提取不出来了。

### `dump_options` 的其它开关

不同版本写法略有差异，常见的有：

| 配置 | 作用 | 建议 |
|---|---|---|
| `dump_include_index_buffers` | 导出索引缓冲 | 开 |
| `dump_include_vertex_buffers` | 导出顶点缓冲 | 开 |
| `dump_include_textures` | 导出贴图 | 开 |
| `dump_include_cb_buffers` | 导出常量缓冲 | 开（骨骼矩阵常在） |
| `deduped` | 去重保存 | 见下 |

### `deduped` 的取舍

3Dmigoto 有「内容相同只存一份」的机制。

**开着的好处**：一个大场景里同一个顶点缓冲被 200 个 draw 引用，只存一份，省几百倍空间。

**开着的坏处**：文件名变成内容哈希，你必须解析 log 才能找到真实文件。

**关掉的好处**：文件名就是逻辑名，`000038-ib=7ad7e69e-vb0....buf` 直接能读，脚本简单很多。

**关掉的坏处**：空间爆掉。一个 8000 draw 的帧可能产生几十 GB。

::: tip 我的建议
**保持 deduped 开着**，在脚本里老实解析 log。

理由：解析 log 是**一次性的工程成本**（写一个函数，二十行），而关掉 deduped 是**每次抓帧都付出的成本**（几十 GB、拷贝极慢）。而且有些版本的 3Dmigoto 在超大帧下会因为不 dedup 而把磁盘写满，dump 直接失败。

教程里所有脚本都走 log 解析，你抄过去就能用。
:::

## 抓帧的时机

3DMigoto 的 FrameAnalysis 通常是按 **F8** 触发。有些版本是 F8 抓一帧，有些是 F8 开始连续抓、再按一次停止。

抓帧的关键是**让想要的模型出现在画面里**：

- 想要角色的身体 → 转到能看到正脸的角度，确保角色完全在视野内
- 想要某个武器 → 让它别被手挡住
- 想要某个 UI 元素 → 保证它在屏幕上显示

::: warning 视角会影响结果
模型被视锥体裁掉（不在视野里）就**不会被绘制**，也就不会出现在转储里。

同样，如果角色被别的物体遮挡，后面的部分可能被裁掉。抓帧时转一转视角，确保目标完整可见。
:::

## 抓多次、抓不同场景

单次转储只能看到那一帧被画的东西。想拿到完整信息，可能需要抓两三次：

| 场景 | 抓什么 |
|---|---|
| 角色静止站立 | 拿到标准姿势、完整贴图 |
| 角色做动作 | 对比姿势，确认哪份是 T-pose |
| 换一套服装 | 拿到多套贴图、多个 IB |

## 抓到之后先别急着开工

打开目录看几件事，能提前避掉很多坑：

### 1. 确认 `log.txt` 存在且不小

```bash
ls -lh log.txt
```

几 MB 是正常。几 KB 说明 `calls=1` 没开，这个转储废了，要重新抓。

### 2. 数一下 IB 有多少个

```bash
# 平铺形态
ls *ib=*.txt | wc -l

# deduped 形态（真实文件在 deduped 里）
ls deduped/*topology*.txt | wc -l
```

几十到几百个都正常。太多（几千）说明这一帧画的东西特别多，找目标 IB 会累一点。

### 3. 看 topology 分布

```bash
# 哪些是三角形，哪些是点
ls deduped/*topology=trianglelist*  | wc -l
ls deduped/*topology=pointlist*     | wc -l
```

::: tip 这个小检查有大用处
`pointlist` 的文件数量通常很少（几十个以内），但它们**极其重要** —— GPU 预蒙皮的 T-pose 顶点和骨骼权重就藏在这里。

如果 `pointlist` 数量是 0，你这个转储里**没有** GPU 预蒙皮数据，模型只能拿到已蒙皮的姿势。见[GPU 与 CPU 预蒙皮](/guide/gametype/preskinning)。
:::

### 4. 确认 deduped 里的文件类型分布

```bash
ls deduped/ | sed 's/.*\.//' | sort | uniq -c
```

典型输出：

```
    243 buf
    446 txt
    285 dds
```

如果 `.buf` 数量是 0，说明 `dump_include_vertex_buffers` 没开 —— 这个转储只有描述没有数据，废了。

## 存储与清理

一次完整转储轻松上 1 GB。抓几次就几个 GB。

建议：

- 抓到有用的转储，**立刻归档**到一个专门的目录，重命名成有意义的名字（`FFA-20261117-角色A站立`）
- 不要的转储**及时删掉**，不要攒
- 转储目录**只读对待**，所有产物写到别的目录 —— 避免脚本一不小心改坏原始数据

::: danger 不要修改转储目录
转储是唯一的事实来源。一旦被脚本改坏（比如误写了某个 `.buf`），你就得重新抓帧。

脚本里所有输出路径都指向工作目录，不要指向 dump 目录。
:::
