数据类型到底是什么 ​

「数据类型」是这类工具里最让人困惑的概念。SSMT4 界面上叫这个名字，代码里叫 D3D11GameType，本质上它就是：

一张「每顶点 stride 里的字节，怎么切成一个个字段」的说明书。

这一节把它讲透。

问题的起源 ​

一个 VB 缓冲是纯粹的字节流：

25 73 07 bf  49 d4 2d bd  a8 00 62 3d  48 84 12 bf  e9 c9 48 bf  25 09 75 3e ...
1

没有任何自描述信息。你不知道：

  • 每顶点是 12 字节？28 字节？40 字节？
  • 前 12 字节是三个 float32（坐标）？还是 12 个 uint8（某种打包数据）？
  • 第 13 字节开始是什么？

唯一的线索是 vb 的 .txt 文件 —— 3Dmigoto 从 dx11 的 IASetInputLayout 里读出来，抄成人类可读的格式。

翻译成人话：

字段名语义名格式槽偏移占几字节
POSITION坐标R32G32B32_FLOATvb0012
NORMAL法线R32G32B32_FLOATvb01212
TANGENT切线R32G32B32A32_FLOATvb02416

加起来 12 + 12 + 16 = 40 = stride。这就是一个数据类型。

如果给它起个名字，按业内约定叫 P12_N12_TA16（P=Position 12 字节，N=Normal 12 字节，TA=Tangent 16 字节）。

七个字段的含义：

字段作用举例
SemanticName语义名。Blender 里靠它决定数据往哪塞POSITION / NORMAL / TEXCOORD / COLOR / BLENDINDICES
SemanticIndex同名语义的序号。TEXCOORD0/1/2 就是靠它区分0 / 1 / 2 / 3
Formatdxgi 格式。决定字节怎么解释成数字R32G32B32_FLOAT / R8G8B8A8_UNORM
ExtractSlot从哪个缓冲槽取vb0 / vb1 / vb2 / cs-t0 / vs-t0
ExtractTechnique从哪类 draw 取pointlist / trianglelist
Category逻辑分类。同一 Category 的元素共享一个 stridePosition / Texcoord / Blend
ByteWidth该元素占几字节12 / 4 / 16

ByteWidth 可以省略

JSON 里 ByteWidth 不写也能工作 —— 从 Format 推算就行。

推算规则（SSMT4 和 3Dmigoto 用同一个算法）：对 format 字符串做 3 字符滑窗，看每个通道的位宽求和。

python
def byte_width_from_format(fmt: str) -> int:
    """DXGI_FORMAT_R32G32B32_FLOAT -> 12"""
    total = 0
    b = fmt.encode()
    for i in range(len(b) - 2):
        w1, w2 = b[i + 1], b[i + 2]
        if w1 == ord('8'):
            total += 1          # 8 位 = 1 字节
        elif w1 == ord('3') and w2 == ord('2'):
            total += 4          # 32 位 = 4 字节
        elif w1 == ord('1') and w2 == ord('6'):
            total += 2          # 16 位 = 2 字节
    return total

这个算法为什么能对上

R32G32B32_FLOAT 里有三个 32，每个贡献 4 字节 → 12。R8G8B8A8_UNORM 里有四个 8，每个 1 字节 → 4。

滑窗起点是 i+1，因为 format 里 R 后面紧跟第一个数字，所以 w1 总落在数字的第一个字符上。

Category 这个字段为什么重要 ​

Category 是最容易忽略但最关键的一维。

规则：同一 Category 的所有元素，物理上必须在同一个缓冲里，首尾相接。

所以：

Category = Position  →  POSITION(12) + NORMAL(12) + TANGENT(16) = stride 40，在 vb0
Category = Texcoord  →  COLOR(4) + TEXCOORD(8) + TEXCOORD1(8) = stride 20，在 vb1
Category = Blend     →  BLENDWEIGHTS(16) + BLENDINDICES(16) = stride 32，在 vb1（有时）
1
2
3

这就是为什么 SSMT4 提取时是「按 Category 逐块处理」的 —— 每个 Category 是一份独立的缓冲，有独立的 stride、独立的顶点数。

顶点数必须一致

同一个模型的所有 Category，算出来的顶点数必须相等。

如果 Position 算出 24068 顶点、Texcoord 算出 24067 —— 说明布局猜错了，或者索引对不上。这是最重要的一个校验点，见跨缓冲顶点数一致性。

四维正交的四个字段 ​

SSMT4 的数据类型里，有四组字段是互相独立的，各管一件事：

字段管什么取值例子
Category逻辑分组Position / Texcoord / Blend / Color
ExtractSlot从哪个 GPU 槽取vb0 / vb1 / vb2 / cs-t0 / vs-t0
ExtractTechnique从哪类 draw 取pointlist / trianglelist
DrawCategory在哪类 draw 的语境下取Position / Texcoord / Blend

它们可以任意组合。全库统计里出现过的组合：

Category → DrawCategory出现次数含义
Position → Position1063标准：坐标从 Position 类缓冲取
Texcoord → Texcoord785标准：UV 从 Texcoord 类缓冲取
Blend → Blend289标准：权重从 Blend 类缓冲取
Blend → Position102权重物理上落在 Position 那路缓冲
Vector → Vector30方向类数据
Normal → Normal18法线单独一类
trianglelist → Position3少见组合

Blend → Position 那 102 处是什么意思？意思是：这个模型把骨骼权重存在了「本来该放坐标」的路上。取数据时必须按 Position 的 draw 语义去定位，而不是按 Blend 的。

ExtractSlot 的取值分布说明了什么

全库统计：vb1 784、vb0 771、cs-t0 283、vb2 202、cs-t1 173、vb4 36、vb3 21、vs-t5 8……

cs-t0 出现 283 次说明：大量游戏的 GPU 蒙皮是靠 compute shader 把结果写进 UAV 的，不只是 vertex shader 的 stream-out。

这直接影响你怎么找 T-pose 顶点缓冲 —— 见GPU 与 CPU 预蒙皮。

命名规则 ​

数据类型名是纯 ASCII 的压缩编码，规则来自 SSMT4 的 gametype_common.py：

[GPU|CPU]_<段1>_<段2>_..._<尾下划线>
1
段含义字节数
P12POSITION，R32G32B32_FLOAT12
P16POSITION，R32G32B32A32_FLOAT16
P8POSITION，R16G16B16A16_FLOAT（也可能 R32G32_FLOAT）8
N12NORMAL12
N4NORMAL，R8G8B8A8_SNORM4
TA16TANGENT16
TA4TANGENT，R8G8B8A8_SNORM4
C4COLOR，R8G8B8A8_UNORM4
C16COLOR，R32G32B32A32_FLOAT16
T8TEXCOORD，R32G32_FLOAT8
T4TEXCOORD，R16G16_FLOAT4
T1-8TEXCOORD1，R32G32_FLOAT8
T2-4TEXCOORD2，R16G16_FLOAT4
BW16BLENDWEIGHTS16
BW8BLENDWEIGHTS，R32G32_FLOAT8
BI16BLENDINDICES16
BI8BLENDINDICES，R32G32_UINT8
BI4BLENDINDICES，R32_UINT4

前缀 GPU / CPU 表示预蒙皮类型。实例：

CPU_P12_N12_TA16_C4_T8_T1-8_T2-8_
GPU_P12_N12_TA16_C4_T8_T1-8_T2-8_BW16_BI16_
1
2

名字只编码字节数，不编码通道结构

P8 可能是 R16G16B16A16_FLOAT（4 通道 × 2 字节）也可能是 R32G32_FLOAT（2 通道 × 4 字节）。两者都是 8 字节，名字里区分不出来。

同理 C4 可能是 R8G8B8A8_UNORM 也可能是 R32_UINT。

所以名字只能当索引用，真要看清结构必须打开 JSON。

SINT / UINT 混用不是错误

有人会问「骨骼索引是整数，为什么还有 SINT 和 UINT 两种？」—— 这是游戏之间的差异，不是预蒙皮类型的差异。读取时用 numpy 的 np.int32 还是 np.uint32 都能拿到正确的 ID（只要数值没超范围）。

数据类型从哪来 ​

三个来源，按使用比重排：

1. 自带库（99% 的情况） ​

SSMT4 安装目录下：

<安装目录>\resources\GameType\<游戏名>\*.json
1

每个 JSON 一个数据类型。目前覆盖 24 个游戏目录，多的一个游戏有 37 个数据类型（ZZMI、NarakaM），少的一个。

只读，不要改

这份库随程序发布，是只读的。要加自己的类型，用下一个来源生成的 zip 导入，不要直接改安装目录。

2. 从转储推导 ​

gametype-analysis 脚本可以扫转储、发现不认识的布局、自动生成 JSON。见从转储推导数据类型。

3. 手写 ​

实在没有的时候自己写一个 JSON。规则就是上面那张字段表。

为什么「选错数据类型」会出事 ​

因为数据类型本质上是一个猜测：

  • 你看到 stride 40，猜是 P12 + N12 + TA16
  • 但真相可能是 P12 + N12 + 16 字节的什么东西

两种解读都能「凑满 40 字节」，都能「顶点数整除」，但解出来的模型完全不对。

这也是为什么 SSMT4 的匹配算法只看文件大小 —— 它没法知道语义，只能验证「大小对不对得上」。要真正校验布局，需要更硬的证据，见拿 vertex-data 反查 stride。
